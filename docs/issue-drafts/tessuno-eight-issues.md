# Eight Tessuno issue drafts

Not created on GitHub. Each section is a candidate issue title and body.

## 1. Resolve Tessuno maintainer and launch ownership

Original roadmap item 1; Tessuno and Apache-2.0 are now selected.

Scope: Record the accountable maintainer, external contribution process and private vulnerability reporting route. Confirm a repository target without claiming the exact Tessuno organization or domain ownership.

Acceptance: Document ownership and source-only release policy; private reports have a tested route and response owner; contributor guidance preserves attribution and adopts no unrequested CLA/DCO.

Boundaries: No account creation, domain purchase, public release or qualified-trust claim.

## 2. Validate SPDX expressions and dependency licenses

License-validation portion of original roadmap item 1.

Scope: Implement comprehensive SPDX expression and per-file/component policy validation, with explicit treatment of development dependencies and generated archives.

Acceptance: Reject invalid expressions and missing/incompatible declarations; preserve official LICENSE and notices; positive/negative fixtures cover policy; inventory distinguishes original work from unvendored dependencies.

Boundaries: No third-party code import, relicensing or paid licensing commitment.

## 3. Qualify one bounded host adapter

Original roadmap item 2.

Scope: Select one supported host and implement an explicit loss report and isolated adapter qualification plan against current official host documentation.

Acceptance: Bind host version, generator and harness revisions; test scope/gate negative cases; run approved isolated smoke tests; retain declared-only status until all mandatory checks pass.

Boundaries: No universal adapter, silent capability upgrade or private host configuration.

## 4. Build original executable iOS fixtures and role evals

Original roadmap item 3.

Scope: Create small original synthetic iOS fixtures with seeded compile and regression failures for the initial iOS Studio workflow.

Acceptance: Approved Mac/toolchain runs record exact versions and all attempts/assertions; demonstrate diagnosis and regression detection; independent review assesses the candidate; failures remain visible.

Boundaries: No private app code, identifiers, accounts, signing or App Store release.

## 5. Implement trusted evidence provenance and release policy

Original roadmap item 4.

Scope: Build a protected verifier that authenticates producers and binds exact candidate, configuration, scope and complete attempt sets.

Acceptance: Reject forged/stale producers, incomplete attempts, digest mismatches, expired/revoked evidence and edited candidates; record redaction/integrity checks; owner approval binds the current action scope.

Boundaries: No self-awarded verified badges or contributor-controlled acceptance policy.

## 6. Review an offline isolated CI lane

Original roadmap item 5 and disabled CI proposal.

Scope: Prepare and independently review the runner, protected harness and immutable dependency/action acquisition for untrusted pull requests.

Acceptance: Demonstrate denied egress, absent secrets/write tokens/host mounts, bounded resources, fixed protected harness and reproducible sanitized readback; enable only after separate authorization.

Boundaries: No privileged events, release/deploy/signing path or trusted artifact consumer.

## 7. Review the exact Tessuno development candidate

Original roadmap item 6.

Scope: Review the verified source import, reversible Tessuno diff, archive readback and license inventory as an unpublished candidate.

Acceptance: Reviewer receives exact source ZIP hash, local history limitation, complete diff, test/build results and expected publication rejection; unresolved gates are explicit; review binds the current candidate.

Boundaries: No public push or claim that the original source review approved new changes.

## 8. Design separately qualified cross-stack extensions

Original roadmap item 7.

Scope: Choose one future stack/capability after the iOS slice and write an ADR plus bounded fixture/evaluation plan.

Acceptance: Each proposed host and capability has independent scope, version, negative cases and evidence requirements; accessibility, localization, StoreKit and device/account profiles stay separately gated.

Boundaries: No scope expansion, runtime support or qualification by implication.
